### 复现与定位

在宿主环境用与启动器完全相同的方式（`RedirectStandardInput/Output/Error`、stdin 管道保持打开、`PYTHONIOENCODING=utf-8`）复刻 `subtitle_cli.ui_bridge live`，并用 `tools/probe_model_load.py`、`tools/probe_asr.py` 分步计时。

1. **`Models()` 偶发长时间停顿。** 干净运行下 `model_deps` 10.0 s、`model_asr` 3.1 s、`model_aligner` 1.4 s，合计 14.6 s；但带音频回环复刻时三次观测到 `model_asr` 段耗时 76 s、105 s 级别，界面在这段时间只有“正在加载模型”，且没有任何日志。停顿的成因尚未定位，但界面与日志已不再依赖它。
2. **真正的硬阻塞：Qwen3-ASR 音频编码器的卷积在 ROCm 上失败。** 稳定复现（两次独立运行）：

   ```text
   transformers/models/qwen3_asr/modeling_qwen3_asr.py:406 forward
       conv_out = F.gelu(self.conv2d1(chunked))
   RuntimeError: miopenStatusInternalError
   ```

   该错误与沙箱无关：在普通 `.venv` 进程里直接调用 `Models.transcribe()` 同样失败，任务会在第一句语音上中止，所以即使模型加载完成也一条字幕都不会产生。`tools/rocm-7.14/bin` 只带 `gfx1030.kdb`，没有 RX 9070 XT（`gfx1201`）的内核数据库；`C:\Users\29279\.cache\miopen` 也不存在，MIOpen 在该架构上没有可用缓存。本次未追查 ROCm 侧原因，改在应用侧规避。
3. **`ui_bridge.read_requests()` 把 stdin EOF 当成停止命令。** 原实现 `finally: stop_requested.set()`：只要 stdin 关闭、为空或被重定向，实时任务会在 1 秒内自行“停止”，报告“已停止，保留已保存字幕”且 0 条字幕。CLI 管道、`< NUL`、任何不保持 stdin 打开的父进程都会触发。
4. **stop 命令带 BOM 时被静默忽略。** `json.loads('\ufeff{"command":"stop"}')` 抛 `ValueError`，被原样吞掉，任务继续采集而父进程以为已发送停止。启动器自身用 `UTF8Encoding(false)` 不写 BOM，因此当前不是故障原因，但同类父进程会中招。

## "正在加载本地组件"长期卡住的根因：Windows 加载器死锁（2026-09-19 03:20–04:20）

**症状。** UI 启动任务后停在"正在加载本地组件"，诊断 JSONL 只有开头几条记录。实测 model_deps 阶段耗时在 03:08:27 的实时运行为 201.2 秒、03:13:23 为 143.1 秒、03:17 的离线运行（`outputs/1.zh.jsonl`）为 164.3 秒，之后才继续；用户观察到点击"停止"后显存和内存反而上升再下降。

**诊断过程。**

1. 给模型加载加逐步心跳（`startup_detail` 的 start/done）后复现：卡点在 `from transformers import AutoModelForMultimodalLM, ...`，最后一条没有配对 `done` 的记录就是卡住的位置。
2. 单线程探针 `tools/probe_startup_imports.py` 导入同一批模块只需 8.7–10.3 秒，5/5 通过；同样由 `spawn-like-launcher.ps1`（与启动器相同的无控制台、stdin/stdout/stderr 管道）启动的 `-m subtitle_cli.ui_bridge` 路径 4/4 卡住。
3. `py-spy dump --native` 给出原生栈：`LoadLibraryExW` → `ntdll!LdrLoadDll` → `ntdll!LdrGetProcedureAddress` → `ntdll!RtlEnterCriticalSection` → `ntdll!RtlSleepConditionVariableCS`。即卡在 Windows 加载器内部，不是慢加载。期间 CPU 时间与 I/O 计数完全冻结，进程没有任何 TCP 连接。
4. 最小复现：`probe-loader-stall.py --reader`（一个守护线程阻塞在 `sys.stdin.read()`，主线程导入 transformers）必卡；同一脚本去掉 reader 线程则不卡。卡在 `numpy._core.multiarray`、`scipy.linalg`、`transformers` 链条上都出现过 —— 凡是原生扩展的 DLL 加载都可能中招。
5. 卡住时 `faulthandler` 每 60 秒仍能转储全部线程栈（证明它不依赖 GIL），但 Python 线程全部无法运行：连"150 秒后 `os._exit(9)`"的硬超时线程也执行不了。**这说明解释器被整体冻结，`startup_step` 的 600 秒看门狗在死锁形态下同样不会触发**（03:23 那次触发 600 秒超时是因为当时加载线程已释放 GIL，属另一种形态）。

**根因。** `ui_bridge` 原来有一个常驻线程阻塞在 `for line in sys.stdin` 上读取启动器 stdin 管道。只要该线程阻塞在管道读，同时另一个线程在加载原生扩展 DLL，Windows 加载器就可能死锁。这也解释了为什么"命令行能跑、UI 卡住"。

**修复。**

- `ui_bridge.StopRequests`：把 stdin 设为非阻塞（`os.set_blocking(fd, False)`，实测在启动器的管道句柄上可用、也可改回阻塞），停止命令改由已有的轮询循环收集：`startup_step` 的 0.25 秒循环、`run_live`/`run_offline` 的每个音频块、`Translator` 的 `/health` 等待循环。**不再有任何线程阻塞在 stdin 上。** 句柄不可轮询时回退到原来的阻塞读线程。
- stdin EOF 仍然不表示停止；BOM 仍然被剥离。
- 停止命令在模型加载阶段即可生效：放弃加载线程，以 `stopped` 结束并用 `os._exit(0)` 跳过解释器收尾（被放弃的线程仍在原生调用里）；加载完成后再检查一次停止标志，已请求停止时不再启动 llama-server。这样也避免了启动器在 60 秒后强杀进程树——强杀正好发生在 HIP 上下文拆除中间。

**修复验证。** 同样的 spawn-like-launcher 条件、同一个实时命令，修复后启动在 21.5 秒内完成：preflight 1.8 s；model_deps 约 8 s（onnxruntime 0.06、transformers 3.08、wtpsplit 3.00、sat_model 1.69、其余 <0.1）；model_asr→model_ready 至 14.656 s；translator_ready 21.531 s；随后 ffmpeg 采集正常运行。修复前同一条件 4/4 卡死。

**新增诊断。** 诊断 JSONL 现在依次记录：`startup`、`startup_host`（python、工作目录、CPU 数、PATH 项数与长度、HIP/MIOPEN/HF 等相关环境变量）、每个导入或模型构造的 `startup_detail`（`start: true` 与 `done` + 秒数）、`startup_cancelled`。每步先写 `start` 再写 `done`，所以最后一条没有配对 `start` 的就是卡点。

**环境结论（回答"命令行 set 的环境是什么"）。** `startup_host` 实测该机器**没有任何** `HIP_VISIBLE_DEVICES`、`ROCR_VISIBLE_DEVICES`、`HSA_*`、`MIOPEN_*`、`TORCH_*`、`HF_*`、`TRANSFORMERS_*`、`PYTHON*` 环境变量；`TEMP`/`TMP` 为标准用户临时目录；PATH 13 项 459 字符（机器级 + 用户级）。即命令行会话与启动器环境一致，慢启动与命令行里 `set` 过的变量无关。系统级也没有安装 ROCm（`C:\Program Files\AMD\ROCm` 不存在），Python 侧 ROCm 只在 `.venv` 里。

## ROCm 与 MIOpen 的结论

- **Python 侧 ROCm 10.0 就是给 gfx1201 的，不需要升级。** `.venv` 里 `torch 2.12.0+rocm10.0.0` + `rocm[libraries,device-gfx1201]==10.0.0`，进程实际加载了 `amdhip64_7.dll`、`MIOpen.dll`、`hipblas.dll`、`libhipblaslt.dll`、`hiprtc0715.dll`、`rocm_kpack.dll`、`c10_hip.dll`、`torch_hip.dll`。实测 `torch.cuda.is_available()=True`、`device_count=2`（0 = AMD Radeon RX 9070 XT，1 = 集显 AMD Radeon(TM) Graphics）、FP16 矩阵乘成功。
- **`tools\rocm-7.14` 与 Python ROCm 无关，只服务 `llama-server.exe`**（llama.cpp b10708 `win-rocm-7.14-x64`），并且只注入那个子进程的 PATH。`bin\gfx1030.kdb` 是 multiarch 归档附带的 MIOpen 内核库；llama.cpp 不使用 MIOpen（它用 hipBLAS/rocBLAS 与自带 HIP 内核），而 gfx120X 归档已解压到同一目录，`--list-devices` 能列出 RX 9070 XT、翻译正常。**两个 ROCm 分属不同进程，不要混装，也不要单独升级其中一个**：llama.cpp 的预编译包与 ROCm 7.14.1 成对发布，单独换 ROCm 会破坏 DLL 匹配；Python 侧换版本则要按部署文档整体更换 torch 组合并重跑验证。
- **MIOpen：可以开启，但当前默认保持关闭，因为它更慢。** Qwen3-ASR 的音频编码器 conv2d 在 gfx1201 上、用 MIOpen 默认的 `MIOPEN_FIND_MODE=FAST` 会抛 `RuntimeError: miopenStatusInternalError`（`.venv\Lib\site-packages\transformers\models\qwen3_asr\modeling_qwen3_asr.py:406` 的 `F.gelu(self.conv2d1(chunked))`），直接中断任务。本次实测：加 `MIOPEN_FIND_MODE=NORMAL` 后 **MIOpen 能正常工作**，转写文本与回退路径完全相同（`森永の美味しい牛乳は濃い青色に牛乳瓶をあしらったデザインのパック牛乳である。`，`ASR_OK`）。同一段 6.98 秒日语音频、同一台机器的对比：

  | 卷积后端 | 模型加载 | 单次转写 | 结果 |
  | --- | --- | --- | --- |
  | MIOpen（`LIVESUB_ENABLE_MIOPEN=1 MIOPEN_FIND_MODE=NORMAL`） | 13.25 s | **13.4 s** | 文本正确 |
  | ATen 回退（默认，`torch.backends.cudnn.enabled=False`） | 12.48 s | **4.7 s** | 文本正确 |

  回退路径快约 2.9 倍，且不需要 MIOpen 的求解器搜索，因此默认仍是回退。要试验 MIOpen 时用：

  ```bat
  set "LIVESUB_ENABLE_MIOPEN=1"
  set "MIOPEN_FIND_MODE=NORMAL"
  "%ProjectRoot%\.venv\Scripts\python.exe" -u "%ProjectRoot%\tools\probe_asr.py"
  ```

  用户会话里直接设这两个变量再启动启动器同样生效（启动器子进程继承环境），`startup_host` 记录会把这些变量一并写进诊断 JSONL。注意 `~/.cache/miopen` 在本次测试后仍不存在，说明 MIOpen 没有落盘缓存，NORMAL 模式的搜索每次都要重做。

## 离线并行流水线与实时悬浮字幕（2026-09-19 05:20–06:10）

### 实时与离线的字幕分离

原实现两种模式共用 `outputs\` 一个目录，实时建议名是 `live-<时间戳>.zh.srt`、离线建议名是 `subtitle.zh.srt`，但切换模式时预览区与「已保存字幕」计数不清空，输出路径也只是在空的时候才改写。现在：

- 实时写入 `outputs\live\live-<时间戳>.zh.srt`，离线写入 `outputs\offline\<视频名>.zh.srt`；`SubtitleView.Begin` 预先建好两个子目录，`SetMode` 每次切换都重设建议路径、清空预览行与计数，并在「已保存字幕」标题上标出当前模式。
- 校验逻辑允许在安装根目录内自动创建子目录（`IsInsideRoot`），安装根目录之外的路径仍要求目录已存在；「已存在 SRT 或同名 JSONL 时拒绝开始」的行为不变。

### 实时等待语音的时间延长

原来没有「等第一句」的概念：只要 VAD 一段时间没有检出语音，实时任务就会以「未检测到可生成字幕的语音」结束，用户先点开始、后按播放时正好撞上这一点。现在：

- 新增 `--no-speech-timeout`（默认 300 秒，0 表示一直等）。第一段语音被检出之前，每 5 秒上报一条 `{"type":"listening","waited_seconds","timeout_seconds","remaining_seconds"}`，界面显示「正在等待语音 · 已等待 mm:ss · 请确认所选设备正在播放声音（N 秒后自动停止）」。
- 语音开始后该计时立即失效，之后的静音不会再结束任务（中途停顿由 Smart Turn 判断，不属于「没有语音」）。
- 超时才以 `no_speech` 失败结束，并保留已写的（空）SRT 与 JSONL 原因。
- `listening` 不是 CLI 阶段名，不会进入 `status.stage`；桥接把它单独发成一种消息，启动器 `TaskRunner.Parse` 新增对该消息类型的解析与「缺 waited_seconds 必须拒绝」的断言。

### 离线不再等播放：分段并行流水线

离线文件已经完整，没有理由按播放速度处理。`--pipeline fast`（默认）把一次任务拆成三段并发：

1. 解码线程持续读 FFmpeg → Silero VAD → Smart Turn，每确认一个完整发言就交给队列（与实时同一套分段代码 `Segmenter`）；
2. 工作线程做 ASR → SaT 分句 → Forced Aligner，识别并发度由 `--asr-workers` 控制（默认 1，因为单条发言已经吃满 GPU）；
3. 翻译通过 llama-server 的 `--parallel` 多槽并发（`--mt-slots`，离线 3、实时 1），并且只在「写盘顺序」上串行。

多段超过 `--max-segment`（默认 30 秒）的发言会在下一个停顿处切开，避免单段过长降低识别与对齐质量；停止时保留的是「完整运行的前缀」：当前句之后的句子与之后所有发言都丢弃，`FastOfflinePipeline.flush` 按段号顺序写盘并检查缺口，所以 SRT 不会出现中间空洞。`--pipeline sequential` 保留原逐段串行路径作为对照。

**正确性对照：** 同一次 `1.mp4`（52.78 秒、18 条字幕）两条路径的 SRT **逐字节相同**（`Compare-Object` 无差异），逐条 `elapsed_seconds` 平均 0.76 s（fast）对 0.85 s（sequential）。

**吞吐实测（`testdata\1.mp4` 十次拼接成 527.74 秒、180 条字幕，7B GPU，同一台机器）：**

| 运行 | 配置 | 墙钟 | 其中启动 | 纯处理 | 相对原速 |
| --- | --- | --- | --- | --- | --- |
| 1 | fast，slots 3 | 95.0 s | 23.2 s | 71.8 s | 7.35× |
| 2 | sequential | 104.8 s | 19.9 s | 84.9 s | 6.22× |
| 3 | fast，slots 3，asr-workers 1 | 112.7 s | 20.7 s | 92.0 s | 5.73× |
| 4 | fast，slots 3，asr-workers 2 | 103.2 s | 20.3 s | 82.9 s | 6.37× |

第 3、4 次说明「同一配置重复之间」的离散可达 20 秒，因此又做了一轮 **fast/sequential 交替、各两次**的对照（消除顺序效应）：

| 轮次 | 配置 | 纯处理 | 相对原速 |
| --- | --- | --- | --- |
| 1 | fast | **69.7 s** | **7.57×** |
| 2 | sequential | 84.8 s | 6.22× |
| 3 | sequential | 84.2 s | 6.27× |
| 4 | fast | **69.8 s** | **7.57×** |

结论：**离线约 6.2–7.6 倍于原速**（527.74 秒的视频约 1.5 分钟出字幕）；并行流水线稳定快 **约 1.21 倍**（69.7/69.8 对 84.2/84.8，组内重复几乎一致），收益来自把翻译与识别重叠、解码不再空转，而不是把 GPU 识别本身加速。`asr-workers 2` 没有稳定收益（第 4 次比第 3 次快但比第 1 次慢），因此默认仍为 1。

### 进度与预估剩余时间（界面）

- CLI 每 `--progress-seconds`（默认 2 秒）发一条 `{"type":"progress","processed_seconds","total_seconds","eta_seconds","speed","decoded_seconds","segments_done","segments_open"}`。全部是实测值：`processed_seconds` 是已完成识别+对齐+翻译的音频秒数，`decoded_seconds` 是已解出的音频秒数，`total_seconds` 来自 `ffprobe`（读不到时缺省），`speed = processed/已用时间`，`eta_seconds` 由该速度外推到剩余音频。
- 启动器底部新增第二个进度条（绿色）：离线运行时显示 `已处理 / 总时长（百分比）· N.NN× 于原速 · 预计剩余 N 分 N 秒 · 已完成 N 段`；`ffprobe` 读不到总时长时改为不确定态并只显示已处理量。任务结束的最后一个报告额外强制发送，所以条不会停在两秒前的值。
- `SubtitleWriter` 之前只记 `startup_*`；现在另记 `offline_pipeline`（模式、槽数、切段上限、文件时长），停止时仍保留已写字幕。

## 翻译模型换 30B 与语音识别模型调查（2026-09-19 05:00–06:00）

### 7B 翻译的速度基线（实测，本机）

用项目自带的 `llama-server b10708`（ROCm 运行时 PATH 注入方式与 `translator.py` 完全一致）、`-c 2048 --jinja`，对 16 条真实字幕长度的英日句子各发一次 `/v1/chat/completions`（temperature 0，max_tokens 512，非流式）：

| 阶段 | 中位耗时 | 生成速度 | 预填充速度 | 模型加载后显存 |
| --- | --- | --- | --- | --- |
| GPU `-ngl 99` | **0.148 s** | 92.8 tok/s | 886 tok/s | 4.93 GiB |
| 部分卸载 `-ngl 20` | 0.727 s | 23.1 tok/s | 65.8 tok/s | 3.24 GiB |
| CPU `--device none -ngl 0` | 1.016 s | 12.1 tok/s | 95.4 tok/s | 0 |

三点观察：本机 7B 全量装进 16 GB 卡后，翻译一句字幕只要 **0.15 秒**，即翻译不是当前流水线的瓶颈（识别才是）；瓶颈不是算力而是**权重搬运**——只要有层留在内存，每 token 都要重新读一遍未卸载的权重，`-ngl 20` 的生成速度因此比全卸载低 4.0 倍；本次日志里第 1 条请求反而最快（0.094 s），因为 llama-server 复用了 slot 前缀（日志原文 `selected slot by LCP similarity`），只有 11–30 个新 token 需要评估。

### 30B 本地部署：能做，但不建议作为默认

- 目标模型是 `Hy-MT2-30B-A3B`（MoE，30B 总参数、约 3B 激活）。官方量化仓库为 [tencent/Hy-MT2-30B-A3B-GGUF](https://huggingface.co/tencent/Hy-MT2-30B-A3B-GGUF)，另有第三方 4bit 转换 [GrahLnn/Hy-MT2-30B-A3B-4bit-GGUF](https://huggingface.co/GrahLnn/Hy-MT2-30B-A3B-4bit-GGUF)。Q4_K_M 约 **18.6 GB**。
- 16 GB 显存放不下权重，还要留 KV cache 与 compute buffer，因此只能卸载约 30–35 / 48 层；按上表 `-ngl 20`（23.1 tok/s）与 `-ngl 99`（92.8 tok/s）的内插，MoE 每 token 只激活约 3B 参数，预计生成落在 **6–10 tok/s**，一句短字幕约 3–6 秒。**这对离线批处理可用，对实时字幕明显偏慢**（实时目前链路允许的单句预算约 1.5 秒）。
- 内存：18.6 GB 权重 + KV cache 在 32 GB 机器上可行，但会挤掉页面缓存，冷启动明显慢于本次实测的 2.7 秒（该数字来自热缓存）。
- 已做的准备：`config.toml` 增加 `hymt_30b`，`--mt-model` 接受 `30b`，界面翻译模型下拉框新增「Hy-MT2 30B-A3B」且**仅在 `models\Hy-MT2-30B-A3B-Q4_K_M.gguf` 存在时才可选**（不会静默换模型，也不会自动下载）。把文件放进 `models\` 即可试用，无需改代码；未下载前该项保持禁用。
- 若只是想要「比 7B 明显更好」，**同系列 14–16B 级别的 Q4_K_M（约 9–10 GB）能全量装进 16 GB 卡**，速度和 7B 同档而质量高于 7B，通常比 30B 更合适；本机没有该文件，未实测。

### 语音识别：当前已是开源最好的选择，可换的只有三件事

本地 `Qwen3-ASR-1.7B`（`models/Qwen3-ASR-1.7B-hf`）的官方说明（模型自带 README）称其「在开源 ASR 模型中达到 state-of-the-art，可与最强的商业 API 竞争」，同系列 0.6B 在并发 128 时可达 2000× 吞吐。相关结论：

- **不建议换成 Whisper large-v3 / Parakeet / SenseVoice 之类**：换框架要重做 VAD-ASR-对齐-翻译整条链并与现有 52 语言/22 种中文方言的识别质量对比，而 1.7B 已属同档最强，收益不足以抵消风险。真正的替代品路线是 `ggml-org/Qwen3-ASR-0.6B-GGUF`（llama.cpp 已支持 qwen3-asr），可省显存，但精度更低。
- **可换的第一件事：0.6B 用于实时**。实时模式对延迟敏感、对长句精度要求低，0.6B 显存更小、吞吐更高；离线继续用 1.7B。未下载、未实测。
- **可换的第二件事：热词偏置**。官方支持 `prompt="Vocabulary: ..."` 形式的领域词表；但**本项目这套 `transformers 5.13.1` 的 processor 会忽略该参数**（实测报 `Keyword argument 'prompt' is not a valid argument for this processor and will be ignored`），要用只能走 chat template 的 system 消息。未接入。
- **可换的第三件事：批推理**。`apply_transcription_request` 支持一次传多条音频，离线理论上可把多段发言合成一个 batch。未实测。
- `attn_implementation` 不能改：把模型切到 `sdpa` 直接抛 `AcceleratorError: CUDA error: invalid argument`，证明当前固定 `eager` 是这台 ROCm 构建上唯一可用的注意力实现。

### 顺带发现并已修复：第一次 ASR/对齐调用有 4–5 秒的一次性开销

同一段 6.98 秒日语音频，**第一次** `transcribe()` 要 4.95–5.11 秒，**第二次**只要 0.70 秒；对齐器第一次 1.34 秒、之后 0.06 秒。这是后端为第一个卷积建算子的一次性成本，不是加载时间。原先它被算进「第一句字幕」的延迟里（实时模式尤其明显）。现在 `Models.warmup()` 在加载完成后用 0.6 秒静音跑一次两个模型，把这笔开销挪到启动阶段：

```text
model load 13.30 s
first real call   5.11 s      <- 修复前
second real call  0.70 s
one second of warm-up costs   0.12 s
real call after warm-up   0.69 s
first aligner call   1.34 s -> aligner call after warm-up 0.06 s
```

预热耗时实测 **5.03 秒**（`startup_detail` 中 `step=warmup`，界面显示「正在预热显卡算子」，启动进度条 65%→75%），失败只记一行、不影响任务。端到端 `sample-ja.mkv` 从 27.3 秒降到 25.3 秒，且第一句字幕不再额外等待约 4 秒。

### 热词/上下文偏置：现在接进去了

澄清两点、并补上实现：

1. **"官方支持 prompt= 不成立"的确切含义。** 官方 README 的写法是 `processor.apply_transcription_request(audio=..., prompt="Vocabulary: ...")`。在本机这套 `transformers 5.13.1` 上，processor 不认这个参数：
   ```text
   [transformers] Kwargs passed to `processor.__call__` have to be in `processor_kwargs` dict, not in `**kwargs`
   [transformers] Keyword argument `prompt` is not a valid argument for this processor and will be ignored.
   ```
   即**那句话本身被丢掉了**，转写结果与不写完全一样。要真的送到模型，只能自己拼 chat template 的 system 消息。
2. **关键在于：模型真的会读它。** `tools/probe_asr_system.py` 用一条**故意错误**的 system 消息做对照（如果模型照做，说明它读了）：

   | system 消息 | prompt tokens | 结果（同一段 6.98 秒日语） |
   | --- | --- | --- |
   | 无 | 109 | `…パック牛乳である。` |
   | "The audio is English. Transcribe it as English." | 120 | `…バック牛乳である。`（`パ`→`バ`，被带偏） |
   | "这段音频是中文的，请用中文输出" | 124 | `…バック牛乳である。`（同上） |
   | `Vocabulary: 森永, 牛乳, パック牛乳, 濃い青色, 牛乳瓶.` | 139 | `…パック牛乳である。`（正确） |

   两条错误指令都改变了输出，证明 system 消息**确实进入模型并影响解码**；热词那条与无消息结果一致，说明这段样本本来就不难，**不能据一条样本断言热词一定提升准确率**，但它会按预期影响识别、成本是 +30 prompt token 与约 0.02 秒。
3. **已接入**：CLI 新增 `--hotwords "<自由文本>"`（`--source-lang` 旁，默认空 = 完全不发 system 消息），`Models(paths, on_progress, on_detail, hotwords)`，非空时 `transcribe()` 走 chat template（system 消息 + 强制语言的前缀），日志里的 `startup` 记录一并写入 `hotwords`。启动器参数卡新增「识别热词（可选）」多行输入框，界面提示写「人名、产品名、术语」，多行会合并成一行；留空时一个参数都不传。
4. 端到端实测（`sample-ja.mkv`，热词「人名与术语：森永, 牛乳, パック牛乳, 濃い青色, 牛乳瓶。」）：无报错，字幕「森永的美味牛奶是一种包装牛奶，其瓶子采用深蓝色设计。」，`startup` 记录含 `"hotwords": "人名与术语：森永, 牛乳, パック牛乳, 濃い青色, 牛乳瓶。"`。逻辑测试新增 2 项（热词必须进 system 消息、留空必须走旧路径且命令行能传到位），共 **31 项通过**。

### 关于"5 分钟的视频为什么花这么久"

先把文件对上：**本项目里只有一个 `testdata\1.mp4`，时长 52.78 秒**（`ffprobe` 实测；项目内没有别的长视频，`sample-en.mkv` 17.36 秒、`sample-ja.mkv` 6.98 秒）。

- 时间花在哪：启动（加载 ASR + 对齐 + SaT + VAD，再加 llama-server）约 **19–22 秒**，这是固定成本、与视频长度无关；然后 52.78 秒视频里有 **18 段发言**，每段要做一次「ASR 编码+自回归解码 → SaT 分句 → 强制对齐 → 翻译」，实测每段约 **0.76 秒**（合计约 14 秒）。所以 fast 34.5 秒 / sequential 35.9 秒。也就是说：**52 秒视频里只有约 14 秒在处理内容**，其余是启动。
- 我用来测吞吐的 **527.74 秒视频不是项目里的文件**：是本次为基准测试临时用 `ffmpeg -f concat -c copy` 把 `testdata\1.mp4` **复制拼接 10 次**得到的 `outputs\offline\long-ja.mp4`（528 秒、180 条字幕），测完已删除。当时 `outputs\1.zh.jsonl` 里那条离线运行显示 `model_asr` 花了 166.39 秒，那是**加载器死锁尚未修复时**的旧记录，不代表现在的速度。
- 换成长视频后启动成本不变，速度优势才看得出来：527.74 秒的视频只需 **69.7 秒**处理（7.57× 于原速）。按 52.78 秒的短视频折算，同样的内容要花约 33 秒，所以**短视频的体验主要由 20 秒启动决定，长视频才是流水线的收益**。

## 悬浮字幕：可拖动、按语音节奏显示、透明度可调

用户反馈三条：悬浮窗拖不动；字幕出现得"很奇怪"，长句很快被后面的短语覆盖；并要求**增加背景与字幕的透明度调节**。

### 根因

**1. 拖不动：`WS_EX_TRANSPARENT` 把整个窗口变成了鼠标穿透。** `SubtitleOverlayWindow.ApplyClickThrough()` 给窗口加了 `0x20`，该样式的语义是**整窗不参与命中测试**，鼠标消息直接穿透到下层窗口——XAML 里拖动条的 `MouseLeftButtonDown` 一次也没有触发过。旁证：松手才写的 `outputs\overlay.json` **从未存在**。

**2. 长句被秒覆盖：字幕是"按句"推送的，而同一语段的 5 句会在同一瞬到达。** `SubtitleView.FlushMessages` 每收到一条 `subtitle` 就覆盖悬浮窗唯一的一个 `Caption.Text`。实测 10:53 那次实时运行：一条 13.9 秒的语段被写成 5 行（19.5→32.9 秒），5 条带着同一个 `elapsed_seconds=2.781` 落盘，也就是在几十毫秒内被连续推给悬浮窗——28 字的第 5 条只亮了零点几秒就被"是的。""没错。"顶掉。

**3. 默认落点会让拖动条跑出屏幕。** 原算式 `Top = 工作区高 × 0.78 − 窗口高`，1180 宽窗口在 1920×1032 工作区里算出 `Top≈717`，窗高 88～360，**窗口下沿落到屏幕外**；即使拖动能用，拖动条也可能在屏幕外够不到。

### 改动

- `launcher\SubtitleOverlayWindow.xaml.cs`：去掉 `WS_EX_TRANSPARENT`，改为**按区域命中**——`WM_NCHITTEST` 在拖动条（顶部整宽）返回 `HTCAPTION`、其余返回 `HTTRANSPARENT`。拖动交给窗口管理器完成（无需鼠标捕获、不激活窗口），字幕区仍然点击穿透、不抢下层软件的点击。落点约束改为整个窗口留在工作区内，拖动/恢复后也保证拖动条可见。
- 新增 `launcher\OverlaySchedule.cs`：按**媒体时间轴**而不是到达顺序显示。每条字幕带自己的起点/终点，显示时长取自身时长（下限 1.2 秒，防止"可是。"这类 0.4 秒的短句一闪而过），到达时已经过去的句子按顺序立即补上，整段说完的最后一句停留 15 秒再清空。语段起点由 `captured_seconds`（每秒推送的采集时钟）与最新字幕终点共同确定，因此不会再回放已经说完的内容。
- `launcher\SubtitleView.xaml.cs`：把一次 `FlushMessages` 里的多条字幕**合成一批**交给悬浮窗（附 `start/end`），并剔除跨批次的重复显示。
- 透明度：右键菜单（拖动条上右键）新增**背景透明度**与**字幕透明度**两个滑杆，另加"恢复默认透明度"。背景滑杆同时作用于底板颜色自身的 alpha 与 `Border.Opacity`（WPF 的 `Opacity` 只能让内容更透明，单改它永远去不掉黑色底板）；字幕透明度下限 10%，避免误操作后完全看不见。两项与窗口位置一起写入 `outputs\overlay.json`（`左,上,背景,字幕`），下次启动自动恢复。

## 离线视频中途报 "unsupported detected source language: Chinese"

| 长度 | 模型判定 |
| --- | --- |
| 0.3s | `Chinese` "对。" |
| 0.5s | `Chinese` "不用。" |
| **0.8s** | `Japanese` "いや無" |
| 3.0s | `Japanese` 正确整句 |

**连带发现**：`pinned Japanese` 时同一段 0.574 秒音频**仍返回 `Chinese`** —— 该 `language` 字段是模型独立预测的输出，`language=` 只是提示、不是约束；不支持的判定直接抛 `ValueError` 并终止整个任务。重复喂同一段 4 次结果完全一致（greedy 解码，`do_sample=False`），所以这是确定性 bug，不是随机抖动。

## 对齐末尾超出音频导致整任务中止（已修复）

界面错误摘要 `字幕不完整：alignment end 3.440s exceeds utterance audio 3.422s at start_sample 2517536` 是致命的：`recognize_segment()` 对任何越界都抛 `PipelineFailure("sentence_mapping", ...)`，整条实时任务随即结束，界面上此前已写入的字幕无法继续增长。

**定位**：`transformers\models\qwen3_asr\processing_qwen3_asr.py` 的 `decode_forced_alignment()` 用 `timestamp_segment_time`（默认 **80 ms**）把时间戳 token 乘成毫秒，`_fix_timestamps()` 的单调性修补还会把越序值吸附到相邻格点。本例 `3.440 / 0.080 = 43.0`，正好比 3.422 秒（54 752 采样）的 PCM 多一格：越界 18 ms，是一格量化误差，不是错字幕。旧校验把它与"识别文本与音频完全不匹配"同等对待，于是每次末尾句被吸附到下一格都会杀掉整个任务；同一次运行里 ASR 原文是正常日语（`さちちゃん なんか、ちっちゃい頃からやってる ことあるんすよね。`），说明识别链路本身是好的。

**修复**（`src/subtitle_cli/pipeline.py`）：

- 新增 `ALIGNMENT_OVERSHOOT_TOLERANCE_SECONDS = 0.2` 与 `MIN_SENTENCE_DURATION_SECONDS = 0.001`。
- 新增 `clamp_to_audio(sentences, duration)`：只把 `start`/`end` 收回到已采集音频长度内，未越界的句子原样返回，返回最大裁剪量与丢弃句数；不按比例、按字数或按上一句重新估算任何时间。
- `recognize_segment()`：越界 ≤ 0.2 秒时收回边界并写 `stage=sentence_mapping, status=alignment_clamped`（含 `alignment_end_seconds`、`trimmed_seconds`、`sentences`、`dropped_sentences`），任务继续；越界 > 0.2 秒仍按 `sentence_mapping` 失败并报出越界幅度；收回后无正时长的句子丢弃并写 `status=alignment_dropped`，不写零时长字幕。
- 规则已写入 `docs\01_Codex开发执行文档..md` 第 3.2 节。

**验证**：`pytest tests -q -p no:cacheprovider` **40 项通过**（原 33 项 + 7 项新增回归）。新增用例走真实 `Pipeline.feed()` → `_commit()` → `recognize_segment()` 链路：1.018 秒对齐对 1.000 秒音频（复刻第一次报障的 18 ms 越界）写成 `00:00:00,000 --> 00:00:01,000` 并留 `alignment_clamped` 记录；512 采样短发言收回后仍写出 `0.032s` 字幕；整段无有效时间的发言（`0.9995–1.100s`）丢弃该句、SRT 为空、任务不失败；1.400 秒对齐对 1.000 秒音频仍抛 `PipelineFailure`；末尾句被压成一点时只丢该句、前两句按原时间写入，任务继续。

## 短句被压成一个时间点导致整任务中止（已修复）

第二次报障：`F:\...\hhd800.com@CAWD-881.mp4` 离线跑到第 96 条字幕后中止，界面显示 `字幕不完整：sentence has no positive alignment duration`，阶段 `sentence_mapping`，诊断文件名 `subtitle1.zh.jsonl`。

**定位**：同一份 JSONL 里有 96 条字幕、4 条 `empty_transcript`、1 条 `alignment_clamped`（`alignment_end_seconds=3.44`、`trimmed_seconds=0.018`，正是上一节修掉的那个越界），以及最后一条失败记录：`{"stage": "sentence_mapping", "error": "sentence has no positive alignment duration", "input": "F:\\...\\CAWD-881\\hhd800.com@CAWD-881.mp4", "exit_code": 1}`。第 96 条字幕是 `297.57–298.45s` 的 `啊，对了。`，说明中止发生在它之后的那段发言里。

这次致命点在 `build_sentences()` 内部，比上一节更靠前：`if items[-1]["end_time"] <= items[0]["start_time"]: raise PipelineFailure("sentence_mapping", "sentence has no positive alignment duration")`。该报错只有这一条触发路径，即那段发言里至少有一个句子（很可能是末尾的短句）的全部对齐项落在同一时间点上。对齐器的时间戳是 80 ms 一格的 token 栅格（`processing_qwen3_asr.py` 的 `timestamp_segment_time`），**短于一格的句子就会这样**，于是每出现一次这样的短句就杀掉整个任务。也就是说上一节只修了"越界"这一条路，同一类分辨率下限还有第二条路没修。

顺带定位到第二处相关的错误拒绝：单调性校验把"该句起点 < 上一句终点"当作失败。被压成一点的句子没有自己的位置，它的起点回到上一句之前是正常的，旧校验却因此再报一次 `invalid or non-monotonic alignment time`。

**修复**（`src/subtitle_cli/pipeline.py`）：

- `build_sentences()`：不再对单个句子的零时长报错，改为计数；`items` 校验拆成两项，单调性游标 `previous_end` **只在有效句子上推进**，被压成一点的句子不再触碰它。仅当整段发言一句有效时间都没有（`collapsed == len(result)`）时仍抛 `sentence_mapping`（此时连句界都无从映射）。
- `clamp_to_audio()`：把被压成一点的句子**丢弃并计数**（`untimed_sentences`），不补时间点、不按比例摊开；其余句子保持原时间，只做收回音频边界与单调推进。
- `recognize_segment()`：写 `status=alignment_clamped`（新增 `untimed_sentences`、`grid_seconds`），全部句子都被丢弃时再写 `status=alignment_dropped`；两种情况下任务都继续。
- 规则已写入 `docs\01_Codex开发执行文档..md` 第 3.2 节（含"不得给无时间句补时间点"）。

**验证**：`pytest tests -q -p no:cacheprovider` **40 项通过**（本轮的 3 项新用例：末尾短句被压成一点时只丢该句、前两句按原时间写入并继续；中间句被压成一点时不影响已测得的句子；整段无任何有效时间时仍按 `sentence_mapping` 失败）。

**未验证**：未重跑 `CAWD-881.mp4` 全片，因此修复后的字幕总条数、丢句数量与翻译质量都还没有实测数据；下一次运行请用 `grep alignment_clamped` 与 `untimed_sentences` 统计。

## 实时采集音质改为设备原生采样率（2026-09-19）

用户要求「修改使用 UI 时的采集音频质量，使用最高码率」。实时采集链路原来向设备索取 `-ac 1 -ar 16000`，即让设备滤波器把 96 kHz 立体声降到 16 kHz 单声道再交给我们。

**实测设备能力**（`tools\ffmpeg\bin\ffmpeg.exe -list_options true -f dshow -i audio="virtual-audio-capturer"`，0.22 s）：

```text
[in#0]  Pin "Capture Virtual Audio Pin" (alternative pin name "1")
[in#0]   ch= 2, bits=16, rate= 96000
```

该设备只暴露这一个格式：**96000 Hz / 2 ch / 16 bit**，因此原命令必然由设备侧完成 6:1 降采样。16 bit 是设备上限，没有更高位深可要；"最高码率"在 PCM 管线上等于"最高采样率 + 无中间损失"。

**改动**：

- `src\subtitle_cli\audio.py`：新增 `device_capture_format()`（解析 `-list_options`，取最高采样率，失败退回 48 kHz 立体声，**绝不因此失败任务**）、`capture_filter()`（显式抗混叠与抖动）、`FFmpegInput(capture_format=...)`。设备按其原生格式打开，唯一一次 16 kHz 单声道转换由 `highpass=f=20,aresample=16000:phase_shift=24:filter_size=256:cutoff=0.97:dither_method=shibata,aformat=sample_fmts=s16:channel_layouts=mono` 完成。
- **SoXR 不可用**：本机 FFmpeg 在 `-h filter=aresample` 中列出 `resampler=soxr`，但实际运行报 `Requested resampling engine is unavailable`，整个 filter graph 失败。已实测确认并改用 swresample 的最高质量参数，取舍写在该函数的 docstring 里。
- `src\subtitle_cli\cli.py`：`run_live()` 探测格式并在**第一块 PCM 上**把格式随采集回调一起上报（不在任何音频到达前上报，否则"采集开始"与"卡死"无法区分）。
- `launcher\TaskRunner.cs` / `SubtitleView.xaml.cs`：新增 `capture_format`/`capture_quality` 字段，界面「采集中」一行显示 `采集时长 … | 已保存 … | 采集 96000 Hz / 2 ch`。
- 顺带修复采集线程的一个真实缺陷：原代码在 `stop` 置位时**先判断后入队**，手上那块 PCM 会被丢掉；现在先入队再于下一块退出，停止不再吞掉进行中发言的音频。

**实测**（真实设备，非 mock）：

```text
probed format: 96000 Hz / 2 ch
args: -f dshow -i audio=virtual-audio-capturer -ar 96000 -ac 2 -af highpass=f=20,aresample=16000:... -f s16le pipe:1
blocks=94 samples=48128 seconds=3.008 wall=0.50s
```

设备以 96 kHz 打开、滤波器图正常、3.008 秒 PCM 在 0.50 秒内交付（6.02× 实时），管道内仍是 16 kHz 单声道 s16le，`media_time()` 与样本计数的关系未变。

**验证**：`pytest tests -q -p no:cacheprovider` **44 项通过**（新增 4 项：设备原生格式探测与命令行断言、抗混叠参数与"不得使用 soxr"约束、探测失败退回 48 kHz、界面收到采集格式）。`launcher\Tests` 7 项通过，`LiveSub.Tests` 构建 0 警告 0 错误。

**未验证**：没有做「同一段音频新旧链路的识别结果 A/B 对比」，因此"音质提升带来识别提升"目前是推理而非实测；新的默认值需要一次完整实时运行（含模型加载）确认端到端无异常。界面显示采集格式需要重新发布 `LiveSub.Launcher.exe` 才会出现，本次未重新发布。

## 内部采样率不能提到 96 kHz（实测，2026-09-19）

用户要求"16000 太小了，用 96000"。**96000 已经用上了，但只能用在前端**：实时设备按 96000 Hz / 2 ch 打开（见上一节），视频源文件按自身格式解码。进模型前必须回到 16 kHz，这不是可调参数，而是三个模型的训练前提：

| 环节 | 实测约束 |
| --- | --- |
| Silero VAD | `VADIterator does not support sampling rates other than [8000, 16000]`（`silero_vad/utils_vad.py:493`） |
| Qwen3-ASR | `WhisperFeatureExtractor` 传 `sampling_rate=96000` 直接抛错："was trained using a sampling rate of 16000" |
| Smart Turn | `models.py:143` 用同一个 Whisper mel 前端，固定 16000 |
| ForcedAligner | 与 ASR 同源音频前端 |

**不重采样、硬喂 96 kHz 的后果**（`tools\probe_rate_96k.py`，真实模型、同一段 6.98 秒日语，两条链路除采样率外完全相同）：

```text
16 kHz input: 223488 bytes = 6.98 s of samples  ->  language=Japanese (0.74s)
    'パック牛乳の…'（正常日语，与既有验收记录一致）
96 kHz input: 1340928 bytes = 6.98 s of samples ->  language=Japanese (0.18s)
    ''（空）
```

96 kHz 样本被 16 kHz 前端按 6 倍时长摊开，语音超出观察窗，转写直接返回空字符串——**得到的是垃圾字幕，不是更好的字幕**。

**离线管道码率（实测）**：`-map 0:a:0 -vn -af aresample=16000:async=1:first_pts=0 -ac 1 -ar 16000 -f s16le pipe:1`，16 kHz 单声道 16 bit = **固定 256 kbit/s**（481640 字节 / 15.051 秒）。源文件 `sample-en.mkv` 的音轨是 48 kHz 单声道 768 kbit/s；管道比源低的那些位，全部是模型用不到的部分。三条离线入口（`cli.py:216`、`cli.py:256`）都走这一行。

**未改动**：中间管道仍为 S16LE。16 bit 的量化噪声约 −96 dBFS，低于真实录音底噪，改浮点管道没有可测量的收益，只会改动块大小与已验收的时间戳。若仍要提升音质，唯一有效方向是前端与降采样（前端已做到设备上限，降采样参数见上一节）。
